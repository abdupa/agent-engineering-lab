# AI Engineering Laboratory Study Guide

Edition: **v0.5 — released curriculum through Retrieval Engineering**.

This is the canonical learning source, synthesized from the repository release
records. A repository release does not imply deployment, package publication or a
Git tag. Exercises invite study; they do not certify learner mastery.

**v0.5 Retrieval Engineering is released.** Its scope includes deterministic
retrieval mechanics and structural citation checks, not real embedding-model quality.
Consult [CURRENT](../CURRENT.md) for task status and release records for final scope.
Historical milestone wording in ADRs describes when decisions were introduced.

Update this guide at formal release completion or when a task explicitly requests

## 1. Engineering mindset and repository operating model

Requirements drive architecture. Start with the smallest design that satisfies a
real requirement; earn added complexity with evidence. Use deterministic software
for validation, arithmetic, permission checks, ordering and budgets. Use AI for
probabilistic decisions while keeping their execution under deterministic control.

The primary application is a NestJS/TypeScript modular backend. Framework use does
not eliminate responsibility boundaries. An interface earns its place by isolating
a real dependency or enabling a useful test seam; a future roadmap item alone does
not justify a database, queue, service, framework or abstraction.

Start work with [AGENTS](../../AGENTS.md), [CURRENT](../CURRENT.md), the active SPEC
and relevant ADRs. The [BLUEPRINT](../BLUEPRINT.md) supplies long-term direction;
it does not authorize implementation. Follow explicit user instructions first,
then active SPEC, relevant ADRs, AGENTS and repository conventions. Work on one
active task and stop before the next. Record implemented behavior, evidence and
limitations in the repository rather than relying on chat history.

The current [decision policy](../DECISION_POLICY.md) governs engineering work:

| Level | Authority                                                          | Example and constraint                                                                                   |
| ----- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| L1    | Decide, implement, test and report autonomously                    | Local fixture structure or pure helper; low-risk, reversible and inside scope                            |
| L2    | Decide autonomously; record an ADR when architecturally meaningful | Small internal interface preserving existing boundaries and requiring no infrastructure                  |
| L3    | Request authorization before implementation                        | Security redesign, persistent storage, breaking public API, major framework or released-invariant change |

Missing detail alone is not a reason to stop. Classify consequences. Prefer existing
dependencies, explicit contracts, local computation and measurement before adding
frameworks, distribution or optimization. Runtime validation, safe errors, testing
and documentation are part of the feature.

The current canonical check is `pnpm verify`: formatting check, lint, typecheck,
tests, build and `git diff --check`. It does not run the manual live smoke. Earlier
release records list these checks individually; the command was composed later as
repository governance, not retroactively shipped application behavior.

## 2. v0.1 — Reliable LLM Foundation

The first release accepts a research objective and optional constraints and returns
a structured research plan. It does not perform the research. `GET /health` reports
process liveness, not provider readiness.

```text
POST /research/plan
  -> correlation middleware and HTTP body parsing
  -> ResearchController: validate unknown input
  -> ResearchPlanService: instructions + serialized user data + output schema
  -> ModelProvider -> OpenAIModelProvider -> Responses API
  <- completion/refusal checks, JSON decode, final Zod validation
  <- parsed ResearchPlan through service/controller, or safe HTTP failure
```

The controller owns transport validation and public status mapping. The service
owns planning instructions. ModelProvider defines structured generation in terms
of instructions, input and a Zod schema; the adapter owns SDK details and returns
the schema's parsed result. ResearchModule binds the concrete implementation to
`MODEL_PROVIDER`. A runtime symbol is needed because TypeScript interfaces are
erased. Source dependencies point toward the application contract even though
runtime calls reach the external provider.

Use parsed values after validation, including transformations and stripped fields.
A type assertion cannot validate external data. Valid JSON is weaker than valid
schema data, and valid schema data is weaker than a useful or factual research plan.
HTTP input and model output are different trust boundaries. The service/controller
do not redundantly parse the already validated research output.

The released provider uses `zodTextFormat` with Responses creation, `store: false`,
response checks and final runtime parsing. The SDK owns up to two retries, with a
10-second attempt timeout. The adapter adds a 30-second asynchronous deadline after
schema conversion. Output validation does not trigger another application retry.
These bounds do not preempt synchronous work or guarantee remote cancellation.

| Failure                                | HTTP mapping |
| -------------------------------------- | ------------ |
| Invalid HTTP input                     | 400          |
| Refusal                                | 422          |
| Invalid model output                   | 502          |
| Provider unavailable                   | 503          |
| Timeout                                | 504          |
| Configuration/internal/unknown failure | 500          |

Raw SDK errors stay inside the adapter. A provider authentication failure is not
an authentication challenge to this API's caller. HTTP 200 upstream can still fail
output validation.

A supported UUID request ID is accepted or generated and returned as `X-Request-ID`.
AsyncLocalStorage carries local correlation without adding diagnostic parameters
to domain contracts. Separate generation context counts transport attempts safely
under concurrency. Attempt duration ends at headers/rejection; execution duration
includes body processing and validation. Allowlisted logs omit prompts, payloads,
credentials, authorization values and raw errors. Correlation is not identity or
distributed tracing, and console logging is not durable audit storage.

Study [ADR-001](../adr/ADR-001-nestjs-primary-backend.md),
[ADR-002](../adr/ADR-002-model-provider-abstraction.md),
[ADR-003](../adr/ADR-003-provider-reliability.md),
[ADR-004](../adr/ADR-004-structured-observability.md),
[structured output](../concepts/structured-output.md) and
[provider boundaries](../concepts/model-provider-boundary.md).

## 3. v0.2 — Controlled Tool System

A tool is an explicit deterministic capability, independent of model-vendor tool
formats. Its contract declares name, description, required permissions, input and
output schemas, and an async handler. The example `add-numbers` requires `calculate`
and adds finite JavaScript numbers; floating-point limitations still apply.

```text
Trusted registration -> ToolRegistry (ordered discovery, exact names)
Caller name + unknown input + fresh grants -> ToolExecutor
  -> lookup -> require context and all permissions
  -> parseAsync input -> handler once -> parseAsync output -> parsed result
```

ToolRegistry rejects duplicate names and offers discovery snapshots. It does not
execute or authorize tools. Definitions and permission arrays are copied/frozen;
executable schemas and closures remain trusted shared code.

ToolExecutor checks grants before schema callbacks or invocation. Missing context
means denial even for a permission-free tool; explicit empty grants only suffice
when no permission is required. This local policy does not authenticate a caller
or determine who may issue grants.

Dynamic lookup erases concrete input/output types. The executor's local type
assertion follows parsing against the registered schema; arbitrary caller-selected
generic result types would falsely imply runtime evidence. Parsed input reaches
the handler and parsed output reaches the caller. Finite inputs can overflow, so
addition also needs output validation.

The configurable 5000 ms whole-operation deadline covers policy, input validation,
handler work and output validation. AbortSignal supports cooperative cancellation;
stage checks prevent late work from starting later stages. No tool retries or
per-tool timeout overrides are delivered. Safe errors are `NOT_FOUND`, `DENIED`,
`INVALID_INPUT`, `EXECUTION_FAILED`, `INVALID_OUTPUT` and `TIMEOUT`.

One safe `tool_execution` completion record describes settlement. A late handler
can still finish without producing a second executor summary. Direct handler calls
can bypass the executor: this design relies on trusted composition and is not a
hostile-plugin sandbox, rollback system or exactly-once guarantee.

Study [ADR-005](../adr/ADR-005-tool-contracts-and-registry.md),
[ADR-006](../adr/ADR-006-tool-reliability-and-policy.md) and
[controlled execution](../concepts/controlled-tool-execution.md).

### Mastery questions and exercises

1. Trace `{ left: 2, right: 3 }` with and without `calculate` through
   `apps/api/src/tools/tool-executor.ts`. Which callbacks must not run on denial?
2. Explain why numeric strings fail and an overflowing sum fails at a different
   boundary. Why must callers receive parsed output?
3. Delay input validation past the deadline with fake time, then resolve it.
   Explain why the handler must never start.
4. Let a handler ignore abort. Separate caller settlement from remaining effects.
   Explain why adding retries would require a new effect-safety decision.

## 4. v0.3 — Custom Agent Loop

The agent proposes actions; deterministic code owns permission, validation,
ordering and termination. The released components are composed directly by tests
and application callers; no agent HTTP endpoint or startup agent is delivered.

```text
AgentRunner -> AgentDecisionService -> ModelProvider
AgentRunner -> ToolExecutor -> ToolRegistry -> controlled handler
```

`AgentState` contains a non-empty goal and ordered observations. `AgentDecision`
is either finish with non-empty result text or tool_call with a non-empty name and
JSON-compatible object arguments. Observations record the requested call and either
a validated JSON-compatible executor result or a safe tool failure code. Grants,
budgets, signals, log data and provider objects stay outside this reasoning state.

The installed strict Structured Outputs path could not directly represent the
canonical root union and arbitrary object maps. The decision service therefore
uses a model-facing root wrapper with `argumentsJson`, decodes it, requires an
object and validates the canonical decision. JSON text is a transport choice;
canonical arguments remain objects. This is recorded compatibility evidence for
the installed path, not a claim about every future SDK.

JSON parsing proves syntax, not tool-specific validity. ToolExecutor still owns
the selected tool's schema. The model receives handler-free name/description
records, never registry internals, grants or handlers. AgentDecisionService depends
on ModelProvider, not the OpenAI SDK. See
[ADR-007](../adr/ADR-007-agent-domain-contracts.md).

AgentRunner defaults to six iterations and a single 60000 ms whole-run deadline,
configurable at construction. Each iteration makes one decision and at most one
executor invocation. Finish returns immediately. Exhaustion fails `LOOP_LIMIT`
without an extra forced-answer request. A safe tool failure becomes an observation
and permits another decision within the remaining budgets; no automatic tool retry
is added. Decision/translation failure, invalid decisions, deadline, cancellation
and unexpected internal failure terminate safely.

Successful observations use executor-validated output, then check JSON compatibility.
This ordering is enforced by execution code; the observation schema alone cannot
prove provenance. Finish means structurally valid text, not verified goal completion.

Caller cancellation stops waiting and later stages without redesigning provider or
tool interfaces to promise hard cancellation. One safe `agent_run` summary reports
started decision/executor counts and terminal outcome. A successful run can contain
a failed tool observation. Request IDs are not unique run identifiers.

The reusable [trajectory evaluator](../../apps/api/test/agent-evaluation/evaluate.ts)
uses a fake ModelProvider with the real service, runner, executor and registry.
Six fixtures cover immediate finish, addition, denial, invalid tool input, loop
exhaustion and translation failure. Exact calls, observations, outcomes and decision
counts prove deterministic composition for those fixtures, not live reasoning.
Study [ADR-008](../adr/ADR-008-bounded-agent-loop.md) and
[agent evaluation](../concepts/agent-evaluation.md).

### Mastery questions and exercises

1. Trace `argumentsJson` into object arguments in
   `apps/api/src/agent/agent-decision.service.ts`, then into ToolExecutor.
2. Contrast malformed JSON with valid JSON containing `left: "two"`. Why does one
   terminate decision generation while the other may become a tool observation?
3. Give a runner two tool decisions and a two-iteration budget. Explain why
   successful tools still end in LOOP_LIMIT without finish.
4. Inspect evaluator expectations for permission denial. Why does an executor call
   count not prove a handler executed?
5. Explain what evidence would be needed for a real-model quality claim beyond
   scripted trajectories or the earlier research-provider smoke.

## 5. v0.4 — Stateful Agent Orchestration

This release makes logical progress and caller-driven continuation explicit while
retaining the v0.3 continuous runner. It does not introduce durable workflows.

| Phase                | Data beyond existing AgentState  | Continuation                                      |
| -------------------- | -------------------------------- | ------------------------------------------------- |
| awaiting_decision    | None                             | Eligible with remaining budgets and fresh context |
| awaiting_tool_result | One canonical pending call       | No automatic replay or resume                     |
| completed            | Validated non-empty result       | Inspection only                                   |
| failed               | Existing safe agent failure code | Inspection only                                   |

Pure transitions complete on finish, store a pending tool call, or append a matching
validated observation and return to awaiting_decision. Terminal transitions are
rejected. Call equality ignores object-key order but preserves array order; it is
not an invocation ID or execution receipt. Runtime objects never belong in state.

A version-1 checkpoint wraps logical state, consumed/max iterations and the original
absolute deadline. Restoration validates an owned copy for inspection. Resume
eligibility is a separate check. Only a quiescent awaiting_decision checkpoint may
continue. Pending effects may already have happened without a recorded observation,
so awaiting_tool_result cannot replay automatically. Valid-shaped history or budget
tampering is not detected as forgery by schema validation.

```text
Trusted application -> Orchestrator.advance(checkpoint, descriptions, fresh context)
  -> validate snapshot and budgets -> one decision
  -> finish: completed
  -> tool_call: internal pending state -> ToolExecutor -> matching observation
     -> awaiting_decision
  -> agent failure: failed
```

One advance consumes at most one started decision and invokes at most one tool.
A final-budget tool decision may return awaiting_decision with an exhausted count;
the next advance fails without a model call. Terminal input is returned for
inspection without work. Invalid checkpoint data rejects safely because there is
no valid domain state to return. Existing AgentRunner remains a separate interface,
which creates a maintenance obligation to keep shared policies consistent.

Ordinary checkpoints preserve the absolute deadline: wall time between calls counts.
Intentional pause is a separate serializable control envelope holding remaining
active time. It is permitted only between advances at awaiting_decision with no work
in flight. Pausing with 37 seconds remaining and resuming an hour later leaves
37 seconds. Resume constructs the continuing deadline from that remainder, never
a fresh full budget. Neither operation resets iterations. Fresh permissions are
supplied outside snapshots and remain subject to ToolExecutor enforcement.

Paused data cannot advance until explicitly resumed. Terminal and pending-tool
states cannot pause; cancellation remains terminal. Callers must establish quiescence
and discard old active snapshots. No lock prevents reuse or concurrent advance.

Each advance has one safe `orchestration_advance` completion event; pure transition,
checkpoint and pause helpers have no logging side effects. Tests settle cancellation
or deadline and then complete late provider/tool work: settled snapshots cannot gain
late observations or a contradictory second completion event. Underlying work and
its own logs may continue. This is suppression of late orchestration state effects,
not guaranteed cancellation or rollback.

[ADR-011](../adr/ADR-011-single-iteration-orchestration.md) records a comparison of
the concrete custom path with LangGraph documentation. The small control flow did
not justify framework dependency, adaptation or duplicated transitions. No prototype
or performance benchmark was claimed. A later requirement may justify reevaluation;
a framework would still need ModelProvider, ToolExecutor and domain validation.

Study [ADR-009](../adr/ADR-009-orchestration-contracts.md),
[ADR-010](../adr/ADR-010-checkpoint-resume-semantics.md),
[ADR-012](../adr/ADR-012-intentional-pause.md),
[checkpoint semantics](../concepts/checkpoint-resume.md),
[intentional pause](../concepts/intentional-pause.md) and
[recovery evidence](../concepts/orchestration-observability.md).

### Mastery questions and exercises

1. Locate `apps/api/src/orchestration/orchestration.ts`. Explain why a pending call
   is phase-specific control data rather than another AgentState field.
2. Serialize and restore a safe checkpoint. Name what validation proves and why
   it does not prove trusted history, storage durability or permission.
3. Compare an hour in an ordinary checkpoint with an hour intentionally paused.
   Use `checkpoint.ts` and `pause.ts` to explain the deadline calculations.

## 6. v0.5 — Retrieval Engineering

Retrieval, evidence selection and generation are separate boundaries. Explicit
callers compose chunkDocument, a Retriever, ContextAssembler and
GroundedGenerationService. No retrieval HTTP endpoint or agent integration is wired.
ModelProvider stays generation-only; EmbeddingProvider is embedding-only.

Documents/chunks preserve non-blank text verbatim and trim references. Schema checks
do not establish unique IDs, parent existence or authentic provenance. Fixed windows
default to 500 Unicode code points with zero overlap, skip whitespace-only windows
and assign sequential emitted indexes. IDs encode [documentId, index], not immutable
content identity. Windows can split words/graphemes and useful context.

Lexical retrieval scores distinct shared lowercase Unicode letter/number tokens,
excludes zero matches and ranks descending. SemanticRetriever explicitly embeds
corpus chunks once, then embeds queries during retrieval. Vectors must be finite,
nonempty, nonzero and dimensionally compatible. Scaling before normalization avoids
extreme-magnitude overflow/underflow. Cosine ranks descending with no minimum
threshold: weak or negative matches can return. Both retrievers preserve input-order
ties and truncate to topK. Equal dimensions do not prove a shared embedding space;
cosine scores are not comparable with lexical counts or probabilities.

ContextAssembler selects whole chunks in ranked order under a text-only code-point
budget and stops at the first oversized chunk, without truncating or skipping ahead.
Request-local E1/E2 citations retain chunk/document/source attribution and exact text,
omitting scores and metadata. Instructions, question and serialization are outside
the budget; this is not a provider token limit.

GroundedGenerationService owns instructions and treats supplied text as evidence/data.
Empty evidence returns insufficient_evidence without a model call. Otherwise the
model may answer or decline. Answers require nonempty text and unique citations to
supplied evidence. Request-dependent membership is checked by the service, beyond
the result schema. Valid references do not prove entailment, truth, complete grounding
or prompt-injection immunity.

The reusable evaluator exercises real retrievers with fake embeddings. Precision@K
is distinct relevant hits in the first K positions divided by requested K, including
unfilled positions. Recall@K divides by distinct fixture relevance labels; without
labels it is null. Slice before deduplication. Fixture corpus IDs must be unique,
but duplicate labels cannot inflate metrics. Exact ordering is asserted separately.
Six lexical and four semantic fixtures prove deterministic mechanics, not real
semantic understanding or universal superiority.

Real embedding integration/reliability, filtering, vector storage, hybrid search,
reranking, live quality evaluation and memory remain deferred. In-memory scans and
copies have no measured production performance guarantee. See
[ADR-013](../adr/ADR-013-retrieval-domain-contracts.md),
[ADR-014](../adr/ADR-014-deterministic-retrieval-baseline.md),
[ADR-015](../adr/ADR-015-semantic-retrieval-foundation.md),
[ADR-016](../adr/ADR-016-context-and-grounded-generation.md) and
[review](../releases/v0.5/REVIEW.md).

   Predict text, indexes and IDs. Why are IDs not immutable content identity?

3. Trace corpus versus query embedding. What does vector validation fail to prove?

## 7. Distinctions to retain across releases

| Distinction                               | Engineering consequence                                                  |
| ----------------------------------------- | ------------------------------------------------------------------------ |
| Compile-time type vs runtime validity     | Parse external values and use parsed results                             |
| Valid structure vs factual truth          | Schema success cannot certify usefulness or accuracy                     |
| Domain contract vs provider transport     | Translate at the boundary without distorting domain data                 |
| Discovery vs permission vs execution      | Lookup and model selection never authorize a handler                     |
| Observation shape vs provenance           | Runtime code must construct observations from validated execution        |
| Timeout vs stopped work                   | Settlement cannot promise preemption or rollback                         |
| Correlation vs identity/audit             | Diagnostic labels and console logs do not prove unique durable execution |
| Deterministic evaluation vs model quality | Scripted trajectories do not establish live reasoning ability            |
| Restoration vs resume                     | Inspecting valid data does not authorize continuation                    |
| Pause vs checkpoint vs cancellation       | Only intentional pause suspends time; cancellation is terminal           |
| Interrupt vs failure; resume vs retry     | Control changes need not be errors or repeated actions                   |
| Execution budget vs paused wall time      | Preserve remaining active time and consumed iterations                   |
| Logical snapshot vs durable workflow      | Serialization adds no crash safety, locking or exactly-once effects      |
| Execution state vs long-term memory       | Current observations/control data are not a memory subsystem             |

The released system does not provide durable storage, ambiguous-effect recovery,
replay/concurrent-resume protection, authentication/approval workflows, queues,
long-term memory, agent-integrated RAG, multi-agent execution or a hostile-code sandbox. Payloads
are not automatically secret-redacted or size-bounded by JSON compatibility.
Prompt separation does not prove prompt-injection immunity. These limitations are
requirements for future design discussions, not implicit implementation tasks.
